# Решения

Отступления от IMPLEMENTATION-PLAN.md и неочевидные технические выборы.

1. **Без AI-помощника.** Решение владельца проекта от 2026-10-01: только запись. В коде нет вызовов LLM и переменной `LLM_API_KEY`.
2. **Хостинг — Vercel** (план), бесплатного тарифа достаточно. Сначала сайт готовился под Cloudflare Pages по формулировке исходного задания; 2026-10-01 владелец выбрал Vercel. Сайт полностью статический, правила в `vercel.json`: файлы отдаются первыми, затем `/s/:slug/*` → оболочка студии, неизвестный путь → `404.html` (то же приложение). CSP задаётся `<meta>` в каждой оболочке, поэтому не зависит от хостинга. Сборка по-прежнему пишет `_redirects`/`_headers` для Cloudflare Pages как запасной вариант (там `_redirects` применяется даже при совпадении с файлом, поэтому маршруты перечислены явно).
3. **Отдельная оболочка на студию при сборке** (`scripts/build/tenant-shells.ts`), а не динамический манифест. У каждой студии свой `id`/`scope`/`start_url`, свой `sw.js` в своей области и свой префикс кэшей `studio-<slug>`, поэтому две установленные студии на одном телефоне — два независимых приложения. Цена — новая студия появляется на сайте после пересборки; данные студии читаются из базы во время работы.
4. **Данные во время работы — из базы, не из JSON.** `business.json` — источник для конвейера; `tenant:publish` переносит его в Postgres по стабильным ключам. Правки владельца в кабинете помечаются и повторной публикацией не перезаписываются.
5. **Публичный API — функции Postgres (security definer), а не таблицы.** Анонимный клиент не видит таблиц вообще; функции сами считают цену, длительность и студию по `service_id`, клиент их не передаёт. Ошибки возвращаются кодами `{error, hint}`.
6. **Пересечения — `resource_occupancies` + `EXCLUDE USING gist`.** Гонки двух клиентов решает ограничение БД, а не проверка в коде. Многодневные работы — одна занятость на весь интервал.
7. **Токен доступа к записи хранится только как HMAC-хэш.** Ссылка «Моя запись» несёт токен во фрагменте `#t=`, который не уходит на сервер в запросах страниц и не пишется в логи.
8. **Web Push без библиотек.** `supabase/functions/_shared/webpush.ts` реализует RFC 8291 (aes128gcm) и RFC 8292 (VAPID ES256) на WebCrypto: работает в Deno Edge Runtime без npm-зависимостей. Проверено расшифровкой своих сообщений в тестах; доставка через реальные push-сервисы браузеров не проверялась.
9. **Outbox для напоминаний.** Задания в `notification_jobs`, выборка `for update skip locked`, повторы с отсрочкой, удаление «умерших» подписок (404/410). Cron вызывает функцию через `pg_net` с секретом из Vault.
10. **Публичные страницы без supabase-js.** RPC идут обычным `fetch`; supabase-js (auth) грузится только в ленивом чанке кабинета и регистрирует провайдер токена.
11. **Drawer — ветка shadcn на Base UI**, установлен вручную в `src/components/ui/drawer.tsx`; Vaul не используется. Остальной UI — Astryx 0.6.3.
12. **Стеклянная кнопка — liquid-gl** со снимком только `.hero-media`: текст соседних секций в линзу не попадает, подпись — отдельный слой поверх. Нижняя навигация зафиксирована, а liquid-gl не работает с fixed-элементами, поэтому там CSS `backdrop-filter`.
13. **Локальный шлюз вместо Supabase в этой среде.** Docker недоступен, поэтому `scripts/local/gateway.ts` эмулирует REST/Auth/Storage/Functions поверх обычного PostgreSQL 16 с теми же миграциями (`supabase/local/shim.sql` создаёт роли `anon`/`authenticated`/`service_role`, `auth.uid()`, `storage.objects`). Это эмулятор, а не интеграция с Supabase.
14. **Ключи Supabase нового формата.** Публичные адрес и `sb_publishable_…` закоммичены в `.env.production`; `sb_secret_…` только у оператора. Ключи нового формата не JWT, поэтому идут только в заголовке `apikey`; `Authorization: Bearer` отправляется лишь с JWT пользователя (или со старым anon/service JWT). Локальный шлюз эмулирует то же поведение.
15. **Владельцев не регистрируют на сайте.** Вход только по почте и паролю; аккаунт создаёт оператор через `tenant:publish` (admin API). В `supabase/config.toml` и в инструкции регистрация выключена.
